## 5. Objectif du portfolio

Le portfolio doit servir simultanément à :

1. présenter Herinjaka professionnellement ;
2. démontrer ses compétences techniques ;
3. présenter ses vrais projets ;
4. montrer sa capacité frontend ;
5. montrer sa capacité backend ;
6. montrer sa capacité full-stack ;
7. permettre à un recruteur de comprendre rapidement son profil ;
8. permettre à un client potentiel de comprendre ce qu'il peut développer ;
9. montrer la qualité de son travail ;
10. servir de vitrine professionnelle.

Le portfolio doit donc être pensé comme un **produit professionnel**, pas comme une simple page CV.

## 6. Concept général

Créer un portfolio moderne avec une identité visuelle fortement liée au développement Web.

Sources d'inspiration possibles :

- environnement de développement ;
- terminal ;
- code ;
- architecture logicielle ;
- interface système ;
- documentation technique ;
- applications modernes.

> **Limite absolue :** le design ne doit en aucun cas devenir un cliché « portfolio hacker ».

Résultat attendu :

- moderne ;
- premium ;
- élégant ;
- technique ;
- professionnel ;
- original ;
- lisible ;
- performant.

L'identité visuelle doit correspondre à un développeur Web moderne spécialisé dans React / Next.js / Node.js.

---

## 7. Philosophie du design

Le portfolio doit éviter les designs génériques.

### À éviter

- template de portfolio classique ;
- simple grille de cartes ;
- énormes gradients ;
- animations partout ;
- tout cliché « portfolio hacker » ;
- trop de couleurs ;
- trop de glassmorphism ;
- composants visuellement surchargés.

Le résultat doit rester **premium, élégant, moderne, original et professionnel** — jamais un simple clin d'œil « hacker ».

### Principe directeur

Le design doit avoir une vraie personnalité. Le visiteur doit pouvoir reconnaître le portfolio même sans voir le nom.

## 9. Architecture des projets

Partie extrêmement importante du portfolio.

Le portfolio doit être conçu dès le départ pour recevoir **3 à 5 vrais projets professionnels/personnels**. Prévoir au minimum **5 emplacements** de projets.

Les projets doivent être **pilotés par des données** :

```text
src/
├── data/
│   ├── projects.ts
│   ├── skills.ts

│   └── services.ts
```

## 33. Données des projets

Créer un système permettant d'ajouter un projet simplement.

Exemple conceptuel :

```ts
const projects: Project[] = [
  {
    slug: "project-name",
    title: "Project Name",
    featured: true,
    // ...
  }
]
```

Pour ajouter un sixième projet, il doit être possible de modifier **uniquement les données** sans modifier `ProjectCard`, la page Projects ou la structure générale.

> **Règle :** `src/data/projects.ts` démarre **vide** (`[]`) — aucun projet n'est publié ni affiché tant qu'il n'a pas été fourni et validé par Herinjaka. L'exemple ci-dessus est purement illustratif et ne doit jamais être rendu dans l'interface.

## 34. Projet exemple « Gestion des plaintes » — structure uniquement

« Gestion des plaintes » n'est **pas** un projet réel du portfolio.

Il s'agit **uniquement d'un exemple de structure** permettant d'illustrer la façon dont un futur projet réel pourra être modélisé dans les données.

### Exemple illustratif — jamais publié

- **Titre :** Gestion des plaintes.
- **Type :** application Web full-stack permettant de centraliser et gérer les plaintes.
- **Technologies possibles :** React, TypeScript, Node.js, Express.js, MongoDB, JWT, TanStack Query.
- **Fonctionnalités possibles :** authentification, gestion des utilisateurs, création de plaintes, suivi des statuts, recherche, filtrage, pagination, historique, notifications, export PDF, chat.

> **IMPORTANT :** cet exemple ne préjuge pas du contenu réel d'un futur projet. Il ne doit **jamais** être publié, affiché ou référencé comme un projet du portfolio. Les vrais projets (titre, description, rôle, année, technologies, fonctionnalités, screenshots, cover/preview, lien Live, lien GitHub si disponible, étude de cas) seront fournis par Herinjaka avant d'être intégrés.
